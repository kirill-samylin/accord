# Техническое задание: сервис координации ИИ-агентов на разных ПК

Рабочее название: **agent-board**. Версия ТЗ: 1.0, 18.10.2026. Статус: согласовано по вопросам 1–15 в обсуждении с владельцем продукта; открытые решения вынесены в раздел 19.

---

## 1. Назначение и принципы

Сервис нужен, чтобы два и более человека на разных компьютерах, каждый со своими ИИ-агентами (Claude Code, Codex и любые другие инструменты, поддерживающие MCP), могли работать над одним проектом без дублей задач, без двойного захвата работы и с общим местом для вопросов, на которые может ответить любой участник.

Принципы, из которых выводится всё остальное:

1. **Сервис это только плоскость координации.** Он ничего не исполняет, не запускает агентов, не хранит код и не пишет в GitHub. Процесс запускает и останавливает человек на своей машине; агенты работают на его машине; сервис отвечает за взаимодействие агентов разных машин.
2. **Одна сущность работы.** Эпик содержит задачи. Задача имеет ролевую метку. Вопрос человеку это задача с ролью человека. Запрос к одиночной роли на другом ПК это задача с ролью этой роли. Механизм один.
3. **Правила исполняет сервер, а не добрая воля агента.** Захват, доказательства переходов, одиночность ролей, независимость ревью проверяются сервером и отклоняются при нарушении. Что именно проверяется и в каком режиме, задаёт конфигурация проекта.
4. **Всё, что захвачено, арендовано.** Любой захват задачи или одиночной роли это аренда со сроком и продлением. Мёртвый агент освобождает захваченное сам по истечении срока. Человек аренды не снимает.
5. **Универсальность через конфигурацию, а не через код.** Роли, состояния, доказательства, сроки, типы вопросов, области записи, режимы правил описаны в файле конфигурации в репозитории проекта. Процесс проекта «Давинчи 2.0» становится первым шаблоном.
6. **Один экземпляр на проект.** Многопроектности, выбора проекта в API и разграничения доступа между проектами нет. Экземпляр разворачивается под каждый проект отдельно, локально для тестов или на сервере.
7. **Экономия контекста агентов.** Агент получает только открытое и относящееся к его роли. Выполненные задачи, полный журнал и чужие заметки отдаются только по явному запросу. Потолок: 12 инструментов MCP, суммарно не более 3 000 токенов описаний, список инструментов фильтруется по роли.
8. **Открытый исходный код.** Лицензия MIT или Apache-2.0 (решение владельца), публичный репозиторий, документация на английском с русским переводом ключевых разделов.

## 2. Термины

| Термин | Значение |

| Экземпляр | Один запущенный сервис, обслуживающий один проект |
| Участник | Человек или токен агента, от имени которого выполняются действия |
| Человек | Участник, вошедший через GitHub или локальную учётную запись |

| Роль человека | Роль, задачи которой выполняют люди через веб-интерфейс или своего агента |

| Задача | Единица работы для одной роли внутри эпика; вопросы и правки для людей тоже задачи |
| Заказчик | Участник, создавший задачу; ему возвращается результат |
| Исполнитель | Участник, держащий аренду задачи |
| Аренда | Захват задачи или роли со сроком действия и продлением |
| Доказательство | Данные, без которых переход состояния отклоняется: коммит, PR, вердикт, ответ |

| Связь | Направленное отношение между задачами или эпиками |
| Событие | Запись журнала только на добавление |
| Заметка | Короткий опыт, привязанный к роли или эпику, для обмена между агентами разных ПК |
| Шаблон | Готовая конфигурация процесса; первый шаблон это процесс «Давинчи 2.0» |

## 3. Границы

### 3.1 Что сервис делает

- Хранит эпики, задачи, заметки, связи, аренды, события, участников и токены.
- Выдаёт агенту его роль, правила, заметки роли и очередь готового.
- Атомарно захватывает задачи и одиночные роли с арендой.
- Проверяет доказательства переходов и право на переход, переоткрытие, ответ.
- Вычисляет блокировки по связям и снимает их при выполнении блокирующей задачи.
- Принимает webhooks GitHub и прикрепляет PR, статус CI и ревью к задаче как доказательства.
- Отдаёт события по курсору, чтобы координатор на любой машине узнавал изменения.
- Ведёт учёт токенов, времени и возвратов по задачам и эпикам.
- Показывает людям две страницы: «Моя очередь» и «Состояние».
- Отправляет уведомления во внешние системы по контракту исходящего webhook.
- Импортирует существующие задачи из файла.

### 3.2 Чего сервис не делает

- Не запускает и не останавливает агентов, не хранит их контекст.
- Не хранит код, диффы, скриншоты, логи. Только короткий текст и ссылки.
- Не пишет в GitHub: ни метки, ни комментарии, ни статусы, ни слияния. Автослияние настраивается в GitHub.
- Не содержит скриптового языка правил, плагинов, аналитических панелей, чата.
- Не решает, кому направить задачу. Маршрутизацию выполняют агенты по правилам проекта; сервер только не даёт нарушить захват и доказательства.
- Не поддерживает несколько проектов в одном экземпляре.
- Не даёт человеку снимать аренды и занимать роли агентов.

## 4. Участники, идентификация, доступ

### 4.1 Люди

- Вход через GitHub OAuth. Допуск к экземпляру определяет список логинов GitHub в конфигурации либо членство в указанной организации или команде GitHub.
- Локальный режим для разработки и тестов: учётные записи в конфигурации с паролем или токеном, без GitHub. Режим включается флагом `auth.mode: local`.
- Человек может: смотреть обе страницы веба, брать и выполнять задачи ролей человека, создавать и отзывать свои токены агентов, импортировать задачи, смотреть конфигурацию и журнал аудита.
- Человек не может: держать роль агента, снимать аренды, редактировать задачи агентов, кроме полей, разрешённых конфигурацией для ролей человека.

### 4.2 Токены агентов

- Токен создаёт человек в вебе или через CLI. Токен привязан к человеку и имени машины. Срок жизни задаётся при создании, по умолчанию 90 дней.
- Хранится только хеш токена. Значение показывается один раз при создании.
- Все действия агента записываются как «агент `<run_id>` от имени `<человек>` на машине `<machine>`».
- Токен отзывается человеком; активные сессии по отозванному токену закрываются, их аренды истекают по обычному сроку.
- Права токена равны правам человека в пределах ролей агентов. Отдельных областей действия у токена нет; разграничение по ролям делает сессия.

### 4.3 Сессия агента

- Сессия открывается первым вызовом `describe` с ролью, идентификатором запуска и именем машины. До `describe` остальные инструменты отклоняются.
- Одна сессия держит одну роль. Смена роли это новая сессия.
- Список инструментов MCP, который сервер отдаёт сессии, зависит от роли (см. 11.2).
- Любой вызов сессии продлевает её аренды.

## 5. Модель данных

Все идентификаторы целочисленные, выдаются сервером. Человекочитаемый ключ формируется из префикса конфигурации: `E-12`, `T-345`, `N-7`. Внешний идентификатор для перенесённых задач хранится отдельно.

### 5.1 Участник

| Поле | Тип | Описание |
| --- | --- | --- |
| id | int | Идентификатор |
| kind | enum | `human`, `agent_token` |
| login | string | Логин GitHub или локальный |
| display_name | string | Имя для интерфейса |
| owner_id | int | Для токена: человек-владелец |
| machine | string | Для токена: имя машины |
| created_at, revoked_at | datetime | Время создания и отзыва |

### 5.2 Эпик

| Поле | Тип | Описание |
| --- | --- | --- |
| id, key | int, string | Идентификатор и ключ `E-NN` |
| title | string ≤ 200 | Название |
| description | markdown ≤ 16 КБ | Границы, критерий завершения, ссылки на требования |
| state | enum | `open`, `done`, `cancelled` |
| owner_id | int | Человек-владелец; заполняется при создании или первом захвате задачи эпика (правило `epic_owner`) |
| areas | string[] | Области записи из конфигурации |
| priority | int | 1 высший, по умолчанию 3 |
| external_id | string | Ключ из прежней системы, например `TASK-031` |
| created_at, done_at | datetime | Из событий |

Вычисляемые поля: число задач по состояниям, число открытых блокировок, сумма `tokens_spent`, время от первого захвата до `done`.

### 5.3 Задача

| Поле | Тип | Описание |
| --- | --- | --- |
| id, key | int, string | Идентификатор и ключ `T-NNN` |
| epic_id | int | Обязателен |
| title | string ≤ 200 | Название |
| description | markdown ≤ 16 КБ | Цель, входы, границы записи, ожидаемый результат, ссылки |
| role | string | Роль из конфигурации; для людей роль с `kind: human` |
| category | string | Категория из конфигурации роли; для ролей человека это тип вопроса или правки |
| complexity | enum | `low`, `normal`, `high`; для ролей человека влияет на то, кто вправе ответить |
| state | enum | `created`, `ready`, `in_progress`, `done`, `cancelled` |
| requester_id | int | Заказчик: кто создал; ему возвращается результат |
| assignee_id, assignee_run | int, string | Текущий исполнитель и его запуск; пусто, если не захвачена |
| priority | int | 1 высший, по умолчанию наследуется от эпика |
| areas | string[] | Области записи; по умолчанию наследуются от эпика |
| evidence | json | Доказательства по схеме роли: `commit`, `pr`, `verdict`, `verified_commit`, `answer`, `run_summary` и другие |
| tokens_spent | int | Сообщает агент при завершении или в `comment`; суммируется по попыткам |
| attempts | json[] | История попыток: исполнитель, запуск, начало, конец, причина завершения, ссылка на ветку |
| external_id | string | Ключ из прежней системы, например `WORK-812` |
| created_at, ready_at, started_at, done_at | datetime | Из событий |

Вычисляемые поля: `blocked` (есть открытая входящая связь `blocks` или `contract_of` от незавершённой задачи), `lease` (срок текущей аренды), `returns_count` (число переоткрытий).

### 5.4 Связь

| Поле | Тип | Описание |
| --- | --- | --- |
| id | int | Идентификатор |
| from_type, from_id | enum, int | `task` или `epic` |
| type | enum | `blocks`, `contract_of`, `duplicate_of`, `spawned_by`, `related` |
| to_type, to_id | enum, int | Цель |
| created_by | int | Автор |

Семантика:

- `A blocks B`: B не считается готовой, пока A не `done`. При `done` у A блок снимается сразу, в той же транзакции, с событием `unblocked` у B.
- `A contract_of B`: B может начинаться после того, как A достигла состояния, указанного в конфигурации как «контракт поставлен», по умолчанию `done`. Используется для связующих эпиков: контракт поставлен, потребители идут параллельно.
- `A duplicate_of B`: A закрывается как дубль с переносом ссылки; A переходит в `cancelled` с причиной `duplicate`.
- `A spawned_by B`: A создана в ходе B, например запрос к архитектору из задачи разработчика. Используется для возврата результата заказчику.
- `related`: справочная, ничего не блокирует.

Циклы по `blocks` и `contract_of` запрещены на уровне сервера: создание связи, замыкающей цикл, отклоняется с перечислением цикла. Связи между экземплярами не поддерживаются.

### 5.5 Аренда

| Поле | Тип | Описание |
| --- | --- | --- |
| id | int | Идентификатор |
| subject_type, subject_id | enum, int | `task` или `role` (для роли идентификатор это имя роли) |
| holder_id, holder_run, machine | int, string, string | Держатель |
| acquired_at, expires_at | datetime | Срок |
| renewals | int | Число продлений |

### 5.6 Событие

| Поле | Тип | Описание |
| --- | --- | --- |
| id | int | Монотонный курсор |
| ts | datetime | Время сервера |
| actor_id, actor_run, machine | int, string, string | Кто |
| type | string | См. 13.1 |
| subject_type, subject_id | enum, int | О чём |
| payload | json | Старое и новое значение, причина, доказательство, нарушенное правило |

Журнал только на добавление. Исправление это новое событие со ссылкой на ошибочное.

### 5.7 Заметка

| Поле | Тип | Описание |
| --- | --- | --- |
| id, key | int, string | `N-NN` |
| scope_type, scope_id | enum, int или string | `role` с именем роли или `epic` с идентификатором |
| text | markdown ≤ 2 КБ | Сам опыт: что сломалось, как решили, чего не делать |
| source_task_id | int | Обязательная ссылка на задачу, где опыт получен |
| author_id, author_run | int, string | Автор |
| created_at, deleted_at | datetime | Время |

Лимиты из конфигурации: максимальное число и суммарный объём заметок на роль и на эпик. При превышении создание отклоняется с подсказкой удалить устаревшие. Удалять вправе роли из конфигурации, по умолчанию автор и роли с `can_curate_notes: true`.

## 6. Состояния и переходы

### 6.1 Состояния задачи

| Состояние | Смысл |
| --- | --- |
| `created` | Создана, не готова: нет обязательных полей или заказчик ещё дописывает |
| `ready` | Готова к захвату; блокировки считаются отдельно |
| `in_progress` | Захвачена с арендой |
| `done` | Выполнена с доказательством |
| `cancelled` | Отменена с причиной: `duplicate`, `obsolete`, `by_requester` |

«Заблокирована» не состояние, а вычисляемый признак. Задача в `ready` с открытой блокировкой не выдаётся через `next`, но видна в очереди с пометкой.

### 6.2 Переходы

| Из | В | Кто | Условия |
| --- | --- | --- | --- |
| `created` | `ready` | заказчик, координатор | заполнены обязательные поля: эпик, роль, описание, области (если правило требует) |
| `ready` | `in_progress` | только через `next` или `claim` | нет аренды, нет блокировок, роль сессии совпадает, правило владельца эпика |
| `in_progress` | `done` | исполнитель | доказательства по схеме роли; для ролей проверки исполнитель не равен автору проверяемого |
| `in_progress` | `ready` | исполнитель через `release`, сервер при истечении аренды | причина; попытка закрывается в `attempts` |
| `done` | `ready` | роли из матрицы переоткрытия | причина и ссылка на доказательство дефекта; событие `reopened`, `returns_count` + 1 |
| любое, кроме `done` | `cancelled` | заказчик, координатор | причина |
| `cancelled` | `ready` | заказчик, координатор | причина |

Переходы, не перечисленные в таблице, отклоняются.

### 6.3 Доказательства по ролям

Схема доказательств задаётся в конфигурации для каждой роли. Сервер проверяет наличие полей и их формат, но не содержание. Примеры для шаблона «Давинчи 2.0»:

| Роль | Обязательные поля `evidence` при `done` | Дополнительные проверки |
| --- | --- | --- |
| `developer` | `commit` (SHA-1 или SHA-256), `pr` (URL), `run_summary` (строка ≤ 1 КБ: команды и результаты) | PR существует в данных webhook, если интеграция включена |
| `reviewer` | `verdict` (`approve`, `changes_requested`, `blocked`), `verified_commit`, `findings` (строка) | исполнитель не равен автору `verified_commit` (по данным webhook или полю `commit` проверяемой задачи) |
| `security` | то же, что `reviewer` | то же |
| `design-reviewer` | `verdict`, `verified_commit`, `screens` (ссылки) | то же |
| `tester` | `run_id`, `verified_commit`, `result` (`passed`, `failed`, `not_run`, `not_applicable`), `run_summary` | |
| `analyst`, `architect` | `artifact` (ссылки на REQ, ADR, контракт), `summary` | |
| `human` (вопрос) | `answer` (строка) | отвечающий входит в список допустимых для категории и сложности |
| `design-owner` (правка дизайна) | `commit`, `pr` | |

Поле `tokens_spent` рекомендуется при любом `done`, но не обязательно: его отсутствие записывается как «неполные данные» в статистике.

### 6.4 Переоткрытие

Матрица в конфигурации: какая роль может переоткрыть задачу какой роли. Пример: `tester` и `reviewer` переоткрывают задачи `developer`; `developer` переоткрывает задачи `analyst` и `architect`; `human` переоткрывает любые. Переоткрытие создаёт событие `reopened`, задача возвращается в `ready`, прежний исполнитель не назначается автоматически.

### 6.5 Состояния эпика

`open` → `done` только когда все задачи в `done` или `cancelled` и нет открытых связей `blocks` на задачи эпика. Переход делает координатор или человек; сервер проверяет условие. `cancelled` с причиной. Переоткрытие эпика: создание новой задачи в `done`-эпике автоматически возвращает его в `open` с событием.

## 7. Аренды

### 7.1 Общие правила

- Аренда создаётся при захвате задачи или одиночной роли. Срок из конфигурации: `leases.task_ttl` и `leases.role_ttl`, по умолчанию 15 минут.
- Любой вызов MCP или REST из сессии продлевает все аренды сессии на полный срок.
- Для молчаливых операций (длинные тесты, сборка) агент вызывает `heartbeat` или продлевает любым вызовом. В конфигурации задаётся `leases.max_silent`, подсказка агенту в `describe`: «вызывай `heartbeat` не реже, чем раз в N минут».
- По истечении срока сервер в фоновой проверке (каждые 30 секунд) закрывает аренду: событие `lease_expired`, задача из `in_progress` в `ready`, попытка закрывается с причиной `expired`, ссылка на ветку из попытки сохраняется, чтобы следующий исполнитель начал с неё. Для роли: роль освобождается.
- Человек не снимает аренду. Единственный способ освободить досрочно это `release` самой сессией или остановка агента с ожиданием срока.
- Один исполнитель держит одну задачу. `next` при уже захваченной задаче отклоняется с её ключом.
- Мягкой брони нет. Координатор сначала захватывает через `next`, потом поднимает агента; если агент не поднялся, аренда истечёт.

### 7.2 Одиночные роли

- Роль с `singleton: true` держится одной сессией в экземпляре.
- `describe` для такой роли пытается взять аренду роли. При занятости возвращает отказ с данными держателя: человек, машина, запуск, срок аренды. Агент не повторяет попытку чаще, чем раз в минуту.
- Запрос к одиночной роли с другой машины оформляется задачей с этой ролью. Сессия держателя увидит её в `next`.
- Если одиночную роль никто не держит, задачи для неё накапливаются в `ready`. Веб показывает в «Состоянии» предупреждение «роль X никем не запущена, N задач ждут».

### 7.3 Правило владельца эпика

Конфигурация `rules.epic_owner` со значениями `off`, `warn`, `strict`:

- `off`: любой агент любой машины берёт любые задачи эпика.
- `warn`: `next` предпочитает задачи эпиков, где владелец равен владельцу токена сессии; чужие задачи выдаются, если своих нет, с событием `rule_warning`.
- `strict`: чужие задачи не выдаются, кроме задач одиночных ролей и ролей из списка `rules.epic_owner.shared_roles`.

Владелец эпика назначается при создании или, если не задан, при первом захвате задачи эпика. Смена владельца это явное действие координатора с событием `epic_handed_off`.

## 8. Очередь готового и алгоритм `next`

Вход: сессия с ролью R, участник P (владелец токена), машина M.

1. Отобрать задачи: `state = ready`, `role = R`, нет текущей аренды, `blocked = false`.
2. Применить правило владельца эпика по 7.3.
3. Для ролей человека: отобрать по категории и сложности задачи, где P входит в допустимые отвечающие.
4. Отсортировать: приоритет задачи по возрастанию, затем `ready_at` по возрастанию, затем приоритет эпика.
5. В одной транзакции: проверить, что у сессии нет захваченной задачи, создать аренду, перевести задачу в `in_progress`, записать попытку и событие `claimed`.
6. Вернуть задачу целиком: поля, описание, связи, последние 10 комментариев, заметки эпика. Выполненные задачи эпика не возвращаются; их ключи доступны по `get`.

При пустой очереди возвращается `{ "task": null, "waiting": { "blocked": n, "leased": m, "no_role": k } }`, чтобы координатор понимал, стоит ли ждать или свободных задач действительно нет.

## 9. Сценарии взаимодействия

Ниже сквозные сценарии. Обозначения: ПК-А и ПК-Б, люди Анна (ПК-А) и Борис (ПК-Б). Инструменты описаны в разделе 11, здесь важна последовательность.

### 9.1 Старт рабочего дня на ПК-Б

1. Борис запускает координатора. Координатор вызывает `describe(role: "coordinator", run_id: "coord-b-2026-10-18a", machine: "pc-b")`.
2. Сервер отдаёт: сводку правил, заметки роли `coordinator`, открытые задачи Бориса, события с курсора, сохранённого координатором в прошлый раз (курсор агент хранит у себя в файле состояния).
3. Координатор вызывает `next` для своей роли, получает пусто с `waiting`, затем смотрит `events(since)` и видит, что две задачи `developer` стали `ready` в эпике Бориса.
4. Координатор поднимает агента-разработчика. Тот вызывает `describe(role: "developer", ...)`, затем `next`, получает задачу `T-345` с арендой.

### 9.2 Разработчику на ПК-Б нужно решение архитектора, который запущен на ПК-А

1. Агент-разработчик на ПК-Б вызывает `create(type: "task", epic_id: 12, role: "architect", title: "Решение по границе IPC для документов", description: "...", priority: 1)` и `link(from: T-401, type: "spawned_by", to: T-345)` и `link(from: T-401, type: "blocks", to: T-345)`.
2. Переводит T-401 в `ready`. Теперь T-345 заблокирована. Разработчик вызывает `release(T-345, reason: "blocked_by:T-401")` или продолжает независимую часть, продлевая аренду.
3. Архитектор на ПК-А, держащий одиночную роль, вызывает `next`, получает T-401, выполняет, вызывает `transition(T-401, to: "done", evidence: { artifact: ["docs/architecture/decisions/ADR-014.md"], summary: "..." })`.
4. Сервер в той же транзакции снимает блок с T-345 и пишет событие `unblocked`.
5. Координатор на ПК-Б видит событие в `events`, поднимает нового разработчика (у Бориса правило «новый агент на шаг»), тот получает T-345 через `next` вместе с ссылкой на T-401 и его доказательством.

### 9.3 Вопрос человеку, на который отвечает любой

1. Аналитик на ПК-А создаёт задачу с ролью `human`, категорией `product_rule`, сложностью `normal`, вариантами ответа в описании (первый по умолчанию) и связью `blocks` на задачу, которая без ответа не может завершиться, если это так. Если работа идёт по умолчанию, связь не создаётся, а в описании указано «работа идёт по варианту 1».
2. Сервер отправляет уведомление по исходящему webhook (если настроен) и показывает задачу в «Моей очереди» всем людям, допустимым для категории.
3. Борис открывает веб, видит вопрос, нажимает «Взять», пишет ответ, завершает. Сервер проверяет, что Борис допустим, записывает `evidence.answer`, переводит в `done`.
4. Агент-заказчик (или координатор заказчика, если агент остановлен) видит `done`, читает ответ. Если ответ устраивает, фиксирует его в требованиях и оставляет задачу `done`. Если нет, переоткрывает с причиной, и вопрос снова в очереди.
5. Если за `questions.escalate_after` (по умолчанию 48 часов) ответа нет, сервер пишет событие `escalated` и повторно уведомляет.

### 9.4 Правка дизайна от владельца дизайна

1. Дизайн-ревьюер на ПК-Б находит дефект. Создаёт задачу с ролью `design-owner` (роль человека, допустим только Анна), категорией `visual_defect`, ссылками на экран и ожидаемое состояние.
2. Анна видит задачу в «Моей очереди», берёт, вносит правку через своего агента или вручную, завершает с `commit` и `pr`.
3. Задача разработчика, зависевшая от правки через `blocks`, разблокируется.

### 9.5 Возврат от тестировщика разработчику

1. Тестировщик на любом ПК нашёл дефект в задаче T-345, которая `done`.
2. Вызывает `transition(T-345, to: "ready", reason: "дефект TC-041", evidence_ref: "T-520")` где T-520 его задача с результатом прогона. Сервер проверяет матрицу переоткрытия: `tester` → `developer` разрешено.
3. T-345 снова в `ready`, `returns_count` = 1, событие `reopened`. Следующий разработчик берёт её с историей попыток и ссылкой на дефект.

### 9.6 Истечение аренды у мёртвого агента

1. Разработчик на ПК-А захватил T-350, его процесс упал.
2. Через 15 минут без вызовов сервер закрывает аренду, пишет `lease_expired`, T-350 в `ready`, попытка с причиной `expired` и ссылкой на ветку `anna/T-350-...` (если ветка была сообщена через `comment` или webhook).
3. Любой разработчик, включая агента Бориса при правиле `epic_owner: warn`, берёт T-350 и начинает с существующей ветки.

### 9.7 Два координатора одновременно создают похожие задачи

1. Координатор ПК-А и координатор ПК-Б создают задачи в одном эпике с пересекающимися названиями.
2. Сервер при `create` ищет открытые задачи того же эпика с совпадением нормализованного названия выше порога `rules.duplicate_check.threshold` (по умолчанию 0,8 по триграммам) и возвращает предупреждение с ключами похожих задач. При `rules.duplicate_check.mode: strict` создание отклоняется до явного `force: true` с причиной.
3. Если дубль всё же создан, координатор закрывает позднюю задачу связью `duplicate_of`.

### 9.8 Обмен опытом между машинами

1. Разработчик на ПК-А при завершении T-350 вызывает `note(create, scope: role:developer, text: "vitest в apps/desktop падает по таймингу при параллельном полном прогоне; запускать test:changed", source_task_id: 350)`.
2. Разработчик на ПК-Б при следующем `describe` получает эту заметку в блоке заметок роли.
3. При превышении лимита заметок роли сервер отклоняет создание и показывает самые старые заметки для удаления. Роль с `can_curate_notes` удаляет устаревшие.

### 9.9 Закрытие эпика агентами двух машин (критерий пилота)

1. Эпик E-12 «Документы в чате» с владельцем Анна. Задачи: анализ (ПК-А), контракт архитектора (ПК-А, одиночная роль), реализация backend (ПК-А), реализация desktop (ПК-Б по явной передаче задачи), ревью каждой реализации агентом другой машины, E2E (ПК-Б), дизайн-ревью (ПК-Б).
2. Все захваты атомарны, ни одна задача не взята дважды, ревьюер всегда не автор, блокировки снимаются автоматически, эпик переходит в `done` после последней задачи.
3. В «Состоянии» видны: расход токенов по задачам и сумма по эпику, время от первого захвата до `done`, число возвратов.

## 11. Интерфейсы

### 11.1 Общие положения

- Транспорт: HTTPS. Сервер умеет сам терминировать TLS с сертификатом из файла или через ACME; допускается обратный прокси.
- MCP: Streamable HTTP по актуальной спецификации Model Context Protocol, авторизация bearer-токеном агента в заголовке `Authorization`. Поддержка OAuth-потока MCP для инструментов, которые требуют его, реализуется как «выдача токена агента через вход человека в браузере» (см. 11.5).
- REST: JSON, те же операции, что в MCP, для CLI, CI и инструментов без MCP.
- Все ответы содержат `server_time` и `cursor` последнего события, чтобы агент мог хранить курсор.
- Ошибки: `{ "error": { "code": "RULE_VIOLATION", "rule": "independent_review", "message": "...", "details": {...} } }`. Коды: `UNAUTHORIZED`, `FORBIDDEN_ROLE`, `NO_SESSION`, `RULE_VIOLATION`, `LEASE_HELD`, `ROLE_HELD`, `NOT_FOUND`, `INVALID_TRANSITION`, `EVIDENCE_MISSING`, `CYCLE`, `LIMIT_EXCEEDED`, `VALIDATION`.

### 11.2 Инструменты MCP

Потолок: 12 инструментов, суммарно не более 3 000 токенов описаний (проверяется при валидации конфигурации по встроенным описаниям). Сессия получает только инструменты своей роли из `mcp.tools_by_role`; при изменении конфигурации сервер шлёт `notifications/tools/list_changed`.

```json
{
  "task": {
    "key": "T-345", "epic": { "key": "E-12", "title": "Документы в чате", "owner": "boris" },
    "title": "Desktop: панель документов в чате",
    "description": "...",
    "role": "developer", "priority": 2, "areas": ["apps/desktop"],
    "requester": "coord-b", "attempts": [],
    "links": [ { "type": "contract_of", "from": "T-401", "state": "done", "evidence": { "artifact": ["docs/architecture/decisions/ADR-014.md"] } } ],
    "comments": [],
    "epic_notes": [ { "key": "N-9", "text": "..." } ]
  },
  "lease": { "expires_at": "2026-10-18T10:57:00+03:00" },
  "cursor": 48226
}
```

Выход при пустой очереди: `{ "task": null, "waiting": { "blocked": 1, "leased": 2, "no_role": 0 } }`.

#### get

Вход: `{ "key": "T-345", "include": ["comments", "events", "done_siblings"] }`. Единственный способ прочитать выполненные задачи и полный журнал задачи. По умолчанию `include` пуст.

#### create

Вход для задачи:

```json
{
  "type": "task",
  "epic_id": 12,
  "role": "architect",
  "title": "Решение по границе IPC для документов",
  "description": "Контекст: ... Вопрос: ... Варианты: 1) ... 2) ...",
  "priority": 1,
  "areas": ["packages/contracts"],
  "category": null,
  "ready": true,
  "links": [ { "type": "spawned_by", "to": "T-345" }, { "type": "blocks", "to": "T-345" } ]
}
```

Выход: `{ "key": "T-401", "warnings": [ { "rule": "duplicate_check", "similar": ["T-398"] } ] }`.

Вход для эпика: `{ "type": "epic", "title": "...", "description": "...", "areas": [...], "priority": 2, "owner": "boris" }`.

#### update

Только для ролей из `can_create`: `title`, `description`, `priority`, `areas`, `category`, `complexity`. Состояние через `update` не меняется.

#### transition

Вход:

```json
{ "key": "T-345", "to": "done",
  "evidence": { "commit": "9f3c…", "pr": "https://github.com/…/pull/212", "run_summary": "npm run test:changed: 41 passed; typecheck ok", "tokens_spent": 184000 } }
```

Выход: `{ "key": "T-345", "state": "done", "unblocked": ["T-346"], "cursor": 48240 }`.

Отказ: `{ "error": { "code": "EVIDENCE_MISSING", "details": { "missing": ["pr"] } } }` или `RULE_VIOLATION` с `rule: independent_review`.

Переоткрытие: `{ "key": "T-345", "to": "ready", "reason": "дефект TC-041", "evidence_ref": "T-520" }`.

#### release

Вход: `{ "key": "T-345", "reason": "blocked_by:T-401", "branch": "boris/T-345-documents-panel" }`. Задача в `ready`, попытка закрывается, ветка сохраняется в попытке.

#### link

Вход: `{ "from": "T-401", "type": "blocks", "to": "T-345" }` или `{ "unlink": true, ... }`. Отказ `CYCLE` с перечислением цикла.

#### comment

Вход: `{ "key": "T-345", "text": "Начал в ветке boris/T-345-documents-panel; тесты затронутых файлов зелёные", "tokens_spent_delta": 20000 }`. Текст ≤ 4 КБ. Комментарий это и место для промежуточных отчётов, и способ сообщить ветку.

#### heartbeat

Вход: `{}`. Выход: `{ "leases": [ { "subject": "T-345", "expires_at": "…" } ] }`. Продлевает все аренды сессии.

#### events

Вход: `{ "since_cursor": 48225, "filter": { "epics": [12], "types": ["unblocked", "task_done", "lease_expired", "reopened", "task_created"] }, "limit": 200 }`. Выход: список событий в сжатом виде и новый курсор. Агент обязан хранить курсор; без `since_cursor` возвращаются только события за последний час.

#### note

Вход: `{ "action": "create", "scope": "role:developer", "text": "...", "source": "T-350" }` или `{ "action": "delete", "key": "N-7", "reason": "устарело после ADR-014" }`. Отказ `LIMIT_EXCEEDED` с ключами самых старых заметок.

### 11.3 Ресурсы и промпты MCP

Ресурсы (чтение по URI, не занимают бюджет инструментов):

- `board://rules` : сжатая сводка конфигурации для роли сессии.
- `board://notes/role/{role}` и `board://notes/epic/{key}`.
- `board://epic/{key}` : эпик со счётчиками и открытыми задачами.
- `board://templates/report/{role}` : шаблон отчёта роли из конфигурации.

Промпты:

- `start-as-role` : «Прочитай правила, возьми задачу через next, работай, отчитайся через transition».
- `coordinate` : «Прочитай события с курсора, подними исполнителей на готовые задачи своих ролей, не бери задачи сам».

### 11.5 Выдача токена агента

1. Человек в вебе: «Токены агентов» → «Создать» → имя машины, срок → показывается значение один раз.
2. Через CLI: `agent-board token create --machine pc-b --days 90` после `agent-board login` (устройственный поток GitHub или локальная учётная запись).
3. Для инструментов агентов, которые умеют только OAuth для удалённого MCP: сервер реализует минимальный OAuth-сервер по спецификации авторизации MCP, где подтверждение в браузере выполняет человек, а выданный токен эквивалентен токену агента и привязан к машине из запроса. Это обязательная часть первой версии, потому что без неё поддержка «любых агентов» не выполняется.

### 11.6 CLI

Одна команда `agent-board` с подкомандами:

- `serve --config /etc/agent-board/server.yaml` : запуск.

### 11.7 Входящие webhooks GitHub

События `pull_request` (opened, synchronize, closed), `check_suite` (completed), `pull_request_review` (submitted). Сопоставление с задачей: ключ по `github.task_key_pattern` в имени ветки или теле PR. Результат: в `evidence` задачи появляются `pr`, `pr_state`, `head_commit`, `ci_status`, `reviews[]`, `merged_at`. ## 12. Веб-интерфейс

Минимальный, серверный рендер плюс немного JavaScript, без тяжёлого фронтенда. Две страницы и служебные.

### 12.1 «Моя очередь»

- Список задач ролей человека, доступных текущему пользователю по категории и сложности, отсортированный как в `next`.
- Карточка: ключ, эпик, заголовок, описание с вариантами, кто спросил, что блокирует, сколько ждёт, срок эскалации.
- Действия: «Взять» (аренда), «Ответить и завершить» (поле ответа или поля `commit` и `pr` для правок), «Переоткрыть» (с причиной), «Комментарий».
- Фильтр по категории и эпику. Закрытые задачи не показываются по умолчанию.

### 12.2 «Состояние»

- Эпики со счётчиками: готовы, в работе, заблокированы, выполнены; владелец; сумма токенов; время с первого захвата.
- Раскрытие эпика: задачи по состояниям, исполнитель и срок аренды, блокировки, возвраты.
- Панель предупреждений: одиночные роли без держателя с числом ждущих задач, просроченные аренды за сутки, несопоставленные webhooks, нарушения правил в режиме `warn` за сутки, задачи людей старше срока эскалации.
- Граф зависимостей эпика в виде списка «что блокирует что», без рисования.

### 12.3 Служебные

- Токены агентов: создать, отозвать, список активных сессий с ролями и машинами.
- Конфигурация: просмотр активной версии и истории применений, только чтение.
- Журнал аудита: события `config_applied`, `token_created`, `token_revoked`, `epic_handed_off`, `rule_warning`, `import`.
- Статистика за период с группировкой по роли, участнику, эпику.

## 13. Журнал событий и статистика

### 13.1 Типы событий

`epic_created`, `epic_done`, `epic_cancelled`, `epic_reopened`, `epic_handed_off`, `task_created`, `task_ready`, `claimed`, `released`, `lease_renewed` (не пишется, только метрика), `lease_expired`, `task_done`, `task_cancelled`, `reopened`, `unblocked`, `linked`, `unlinked`, `commented`, `note_created`, `note_deleted`, `rule_warning`, `escalated`, `webhook_received`, `unmatched_webhook`, `session_opened`, `session_closed`, `role_acquired`, `role_released`, `config_applied`, `token_created`, `token_revoked`, `import`, `correction`.

### 13.2 Статистика

Считается по событиям, не по датам изменения записей. Отдаётся по API и в вебе:

- впервые выполненные задачи за период по роли и участнику; повторное выполнение после переоткрытия считается доработкой;
- завершённые эпики за период;
- активные, заблокированные, готовые задачи по ролям на момент запроса;
- время от первого `claimed` до первого `task_done`, длительность блокировок, возраст очереди, число возвратов;
- токены: сумма по задаче, эпику, роли, участнику за период; доля задач без данных о токенах;
- истечения аренд и нарушения правил за период.

Календарное время не выдаётся за время работы модели. Количество задач не используется как рейтинг.

## 14. Импорт и экспорт

- Формат: JSON Lines, по одной записи на эпик, задачу, связь, заметку. Схема поставляется с сервисом.
- Импорт идемпотентен по `external_id`: повторный импорт обновляет поля, не создаёт дубли.
- Импорт пишет события `import` с источником и хешем файла.
- Переносимые из «Давинчи 2.0» карточки TASK и WORK преобразуются отдельным скриптом проекта (не частью сервиса) в JSON Lines: TASK → эпик, WORK → задача с ролью из карточки, статусы по таблице соответствия, `external_id` сохраняет `TASK-NNN` и `WORK-NNN`. Журналы WORK переносятся как комментарии с исходным временем.
- Экспорт: полный дамп в JSON Lines плюс копия базы SQLite.

## 15. Нефункциональные требования

### 15.1 Стек и развёртывание

- Язык: Go (актуальная стабильная версия). Один статический исполняемый файл для Linux amd64/arm64, macOS arm64/amd64, Windows amd64.
- Хранилище: SQLite в режиме WAL, встроенный, одна база на экземпляр. Миграции схемы встроены в бинарник и применяются при старте.
- Поставка: бинарник в релизах GitHub, образ контейнера, пример `systemd`-юнита, пример `docker compose`.
- Запуск на сервере: один процесс, переменные окружения для секретов (`AGENT_BOARD_GH_CLIENT_ID`, `AGENT_BOARD_GH_CLIENT_SECRET`, `AGENT_BOARD_GH_SECRET`, `AGENT_BOARD_NOTIFY_SECRET`, `AGENT_BOARD_DB_PATH`), конфигурация сервера в YAML (адрес, TLS, путь к базе, режим аутентификации).
- Запуск локально для тестов: `agent-board serve --dev` поднимает экземпляр с локальной аутентификацией и временной базой.

### 15.2 Производительность и надёжность

- Нагрузка расчётная: до 5 человек, до 20 одновременных сессий агентов, до 2 000 задач и 200 000 событий в базе за год.
- p95 ответа любого вызова API при такой нагрузке не выше 50 мс на сервере с 1 vCPU и 512 МБ памяти; память процесса не выше 128 МБ.
- Старт процесса не дольше 1 секунды.
- Все изменяющие операции транзакционны; захват и снятие блокировок атомарны.
- Фоновая проверка аренд не чаще `leases.sweep_interval`.
- Резервное копирование: команда `backup` делает согласованную копию через SQLite online backup; рекомендация запускать по cron.
- Логи в stdout в JSON, уровни `info` и `debug`; метрики Prometheus на `/metrics`.

### 15.3 Безопасность

- Токены агентов хранятся как хеши (SHA-256 с солью), показываются один раз, имеют срок и отзыв.
- Проверка подписи входящих webhooks; отклонение без подписи.
- Подпись исходящих уведомлений.
- Ограничение частоты: не более 20 вызовов в секунду на сессию, не более 5 неудачных входов в минуту на IP.
- Журнал аудита для создания и отзыва токенов, применения конфигурации, передачи эпиков, импорта.
- Валидатор полезной нагрузки предупреждает о строках, похожих на секреты (ключи API, токены) в описаниях, комментариях, заметках; при `rules.secret_scan.mode: block` отклоняет.
- Модель угроз первой версии: злоумышленник с утёкшим токеном агента может создавать, захватывать и закрывать задачи от имени человека в пределах ролей агентов; ущерб ограничен отзывом токена и журналом. Доступ к коду через сервис невозможен, потому что код в нём не хранится.
- Никаких внешних вызовов, кроме GitHub OAuth, входящих webhooks и настроенных исходящих уведомлений.

### 15.4 Тестирование самого сервиса

- Модульные тесты правил, переходов, аренд, графа связей, очереди.
- Интеграционные тесты API с временной базой: все сценарии раздела 9.
- Тест совместимости MCP: подключение Claude Code и Codex к локальному экземпляру, прохождение `describe` → `next` → `transition` на каждом.
- Нагрузочный тест: 20 сессий, 1 000 задач, проверка p95.
- Тест истечения аренд с ускоренным временем.

### 15.5 Документация

- README: назначение, установка, запуск за 5 минут, подключение Claude Code и Codex.
- Справочник конфигурации с описанием каждого поля и режимов правил.
- Справочник MCP и REST с примерами из раздела 11.
- Руководство по написанию шаблона процесса.
- Шаблон «Давинчи 2.0» как пример с комментариями.

## 16. Шаблон «Давинчи 2.0»

Поставляется с сервисом как `templates/davinci.yaml`. Соответствие текущему процессу проекта:

| Элемент процесса | Как выражается в сервисе |
| --- | --- |
| TASK (фича) | Эпик с владельцем-человеком |
| WORK (ролевое задание) | Задача с ролью |
| Открытый вопрос OQ | Задача с ролью `human`, категория `product_rule` или `ux_path`, варианты в описании, первый по умолчанию |
| Промпт Claude Design CD-NNN, импорт DS, визуальные дефекты | Задача с ролью `design-owner` и категорией |
| Независимое ревью | Задача `reviewer` с правилом `independent_review: block` |
| Security, дизайн-ревью, E2E после approve | Задачи соответствующих ролей со связью `blocks` от задачи ревью |
| Одиночный архитектор, создатель задач | `singleton: true` у `architect` и у роли `planner` (если выделяется из координатора) |
| Один разработчик за одно задание | `one_task_per_agent: block` |
| Непересекающиеся области записи | `area_overlap: warn` |
| Отложенные рекомендации | Комментарии к задаче или заметки эпика |
| Журнал расхода токенов | `tokens_spent` при `done` и в комментариях |
| Точка остановки и «Текущее состояние» координатора | Курсор событий и `my_tasks` в `describe`; отдельного документа не нужно |
| Ретест пакетом после приёмки дельт | Задача `tester` создаётся координатором один раз на шаг со связью `blocks` на задачу `developer` |

Что в сервис не переносится и остаётся в репозитории проекта: требования REQ, ADR, контракты, карточки с подробными журналами (как документы), правила кода, Git-процесс.

| 4. Выпуск | Документация, образы, релизы, шаблон «Давинчи 2.0», нагрузочный тест | Сценарий 9.9: один эпик закрыт агентами двух машин по шаблону |

Оценка при разработке агентами по процессу «Давинчи 2.0» с независимым ревью: этап 0 около 3 дней, этапы 1–2 около 6–9 рабочих дней, этапы 3–4 около 4–6 дней. Главная неопределённость: совместимость удалённого MCP с авторизацией у инструментов агентов, проверяется в этапе 0 первой.

## 18. Критерии приёмки первой версии

1. Два человека на разных машинах с разными инструментами агентов закрывают один эпик по шаблону «Давинчи 2.0»; ни одна задача не захвачена дважды; все ревью выполнены не авторами.
2. Одиночная роль, запущенная на одной машине, отказывает второй машине с данными держателя; задача для неё с другой машины выполняется и возвращается заказчику через снятие блокировки.
3. Вопрос человеку виден обоим людям в «Моей очереди», отвечает любой допустимый; агент-заказчик закрывает или переоткрывает.
4. Аренда мёртвого агента истекает и задача возвращается в очередь с сохранённой ссылкой на ветку; человек при этом ничего не делал.
5. Попытка создать явный дубль получает предупреждение с ключами похожих задач; в режиме `strict` отклоняется.
6. Сессия роли получает только инструменты своей роли, суммарное описание не превышает 3 000 токенов; `next` не возвращает выполненные задачи.
7. Заметка, созданная на одной машине, видна агенту той же роли на другой при следующем `describe`; лимит заметок соблюдается.
8. Конфигурация из репозитория применяется командой, невалидная отклоняется, история применений видна в аудите.
9. PR и статус CI появляются в доказательствах задачи после webhook; сервис не делает ни одного вызова к GitHub API.
10. Статистика за период показывает задачи, эпики, время, возвраты и токены по ролям, участникам и эпикам, с пометкой неполных данных.
11. Экземпляр поднимается одной командой локально и одним контейнером на сервере; резервная копия создаётся командой.
12. p95 вызовов не выше 50 мс при 20 сессиях и 1 000 задач.
