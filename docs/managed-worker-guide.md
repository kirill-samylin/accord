# Подключить компьютер к управлению агентами

Инструкция TASK013. Нужен совместимый сервер Accord с `managed_agents:1` и
board schema5, а также новый клиент `agent-board`. Исходники новой функции
сами не обновляют установленный сервер. Рабочий VPS и Mac обновлены отдельной
поставкой 23.10.2026; точная версия и фактическая приёмка —
[TASK013](TASK-013-managed-agents.md). Windows и второй физический компьютер
требуют отдельного запуска; сборка `.exe` не подтверждает их работоспособность.

## Как это работает

На каждом компьютере работает локальный исполнитель Accord — worker. Он
получает команды общего проекта и запускает собственные процессы Codex,
Claude Code или корпоративного Gennadiy (fork OpenCode). В панели видны
компьютер, задание, состояние процесса и история
доставки команд. Уже открытые чаты и процессы других приложений не подключаются.

Для удалённой работы компьютер должен быть включён, иметь связь и запущенный
worker. Открывать порт или выдавать SSH-доступ не требуется. Worker запускается
от обычной учётной записи владельца, с его локальным входом в Codex/Claude.
Accord не получает пароль, подписку или API-ключ модели.

Ниже приведён пример подключения «Давинчи 2.0». Для другого проекта берите
его собственные project ID, токен, папку и отдельный state; не копируйте proof
или разрешения другого проекта. Автоматический цикл по требованию описан в
[отдельной инструкции](automation-guide.md) и требует совместимой версии
сервера/worker и дополнительного локального согласия.

У каждого ПК своя рабочая копия GUI. Общая доска передаёт задания и команды,
а изменения файлов передаются через обычный Git. Одинаковое имя рабочей папки
в Accord не синхронизирует файлы между компьютерами.

Пользователь выбрал взаимное управление: оба участника могут управлять обоими
компьютерами. Каждый владелец явно разрешает второго участника на своём ПК.
Одна роль «Редактор» на доске этого разрешения не выдаёт.

## Быстрое подключение

Команда `agent-board worker setup` проводит владельца по подключению без
ручного редактирования JSON. Она появилась в WORK296; клиент старше этой
версии её не содержит. Запускайте в терминале от своей учётной записи, передавая
только путь к приватному config:

```text
agent-board worker setup --config PRIVATE_WORKER_JSON
```

Команда работает по шагам и ничего не принимает из сети или аргументов:

1. Ищет установленные CLI `codex`, `claude` и `gennadiy` в `PATH` и типичных
   местах (бандл ChatGPT, `~/.claude/local`, `~/.nvm`, Homebrew, `~/.gennadiy`),
   показывает путь и версию каждого и предлагает выбор. Для gennadiy npm-шим
   `gennadiy.cjs` и bash-шим `~/.gennadiy/bin/gennadiy` сами не принимаются:
   команда находит настоящий бинарь `gennadiy-darwin-arm64/bin/gennadiy`.
   Принимаются только абсолютные пути к обычным файлам без символических
   ссылок, как и при ручной настройке.
2. Спрашивает рабочие папки и провайдеров для каждой, режим прав
   (`codex_sandbox`, `claude_permission_mode`, `gennadiy_permission_mode`) с
   пояснением последствий, набор действий Accord без подтверждения
   (`native_mcp_approved_tools`): «только чтение» — `describe`, `next`, `get`,
   `events`; «работа по задаче» — те же плюс `update`, `comment`, `note`,
   `transition`, `release`, `link`; и точные модели `models`, если профиль
   требует конкретную модель.
3. Для нового config дополнительно спрашивает путь к файлу токена, адрес
   сервера, ID проекта, имя машины (значения предлагаются из `connection.json`
   рядом с токеном, если он есть), имя компьютера и каталог состояния. Сам
   токен не запрашивается, не печатается и не попадает в аргументы.
4. Существующий `worker.json` редактируется: `server`, `project`,
   `token_file`, `state_dir`, `controllers` и `automation` не меняются.
   Перед записью выполняется та же проверка, что и при `worker run`, и
   `--version`/`--help` выбранных CLI; при ошибке файл не трогается. Запись
   атомарная, права `0600`; новый каталог создаётся с правами `0700`.
5. Затем команда сама выполняет `worker enroll` для нового компьютера или
   `worker consent` для уже подключённого. На macOS при наличии user
   LaunchAgent `com.accord.gui.worker` служба останавливается через
   `launchctl bootout` на время consent и запускается снова через
   `launchctl bootstrap`; по явному подтверждению бинарь службы заменяется
   копией текущего `agent-board`. Без службы команда напоминает запустить
   `worker run`.

Если consent не удался (нет сети, отказ сервера), config уже сохранён, служба
запущена снова, и достаточно повторить `worker consent`. Код управления второго
участника (`controllers`) по-прежнему добавляется вручную, см. ниже. Ручная
настройка JSON остаётся доступной и описана дальше.

## Подготовить локальные файлы

Нужны собственный токен участника GUI, точный project ID и HTTPS origin из
индивидуального `connection.json`. Токен другого человека не копируют.
Доступ к Git и локальная копия GUI подготавливаются обычным способом.

На Mac храните настройки, токен и state в приватном каталоге вне Git: каталог
`0700`, файлы `0600`. На Windows нужны настоящие ACL: владелец — текущая учётная
запись; доступ только ей, SYSTEM и необходимым локальным администраторам.
Unix mode bits на Windows не заменяют ACL, worker проверяет DACL.
Не публикуйте токен, реальный origin, полный config или state.

Настройка `worker.json` для Mac (все заглушки заменяются локально):

```json
{
  "server": "https://ACCORD_ORIGIN",
  "project": "p_PROJECT_ID_FROM_CONNECTION",
  "token_file": "/ABSOLUTE/PRIVATE/gui.token",
  "state_dir": "/ABSOLUTE/PRIVATE/worker-state",
  "name": "mac-main",
  "machine": "MACHINE_FROM_CONNECTION",
  "controllers": [],
  "executables": {"codex": "/ABSOLUTE/PATH/TO/codex"},
  "codex_sandbox": "workspace-write",
  "workspaces": {
    "gui": {"path": "/ABSOLUTE/PATH/TO/gui", "providers": ["codex"]}
  }
}
```

`workspace-write` означает явное локальное разрешение править выбранную рабочую
копию. Для проверки чтения выберите `read-only`. Другие native правила и
подтверждения не отключаются; отказ разрешения виден как ошибка работы агента.
Модель по умолчанию выбирает установленный CLI. Если профиль содержит конкретную
модель, добавьте её в локальный `models`, например
`{"codex":["EXACT_LOCALLY_ALLOWED_MODEL"]}`. Worker не меняет её на другую молча.

Для native Windows Claude Code замените соответствующие поля:

```json
{
  "server": "https://ACCORD_ORIGIN",
  "project": "p_PROJECT_ID_FROM_CONNECTION",
  "token_file": "C:\\Users\\USER\\.config\\accord-gui\\gui.token",
  "state_dir": "C:\\Users\\USER\\.config\\accord-gui\\worker-state",
  "name": "pc-2",
  "machine": "MACHINE_FROM_CONNECTION",
  "controllers": [],
  "executables": {"claude": "C:\\ABSOLUTE\\PATH\\claude.exe"},
  "claude_permission_mode": "default",
  "workspaces": {
    "gui": {"path": "C:\\Users\\USER\\Projects\\gui", "providers": ["claude"]}
  }
}
```

Нужен native `.exe`; `.cmd`/`.bat`, UNC/network roots и ссылки вместо разрешённой
папки не принимаются. `acceptEdits` можно выбрать только локальным решением
владельца вместо `default`; это не разрешение обходить остальные подтверждения.
Пути и параметры запуска из браузера не принимаются.

Для корпоративного Gennadiy (fork OpenCode) на Mac:

```json
{
  "server": "https://ACCORD_ORIGIN",
  "project": "p_PROJECT_ID_FROM_CONNECTION",
  "token_file": "/ABSOLUTE/PRIVATE/gui.token",
  "state_dir": "/ABSOLUTE/PRIVATE/worker-state",
  "name": "mac-main",
  "machine": "MACHINE_FROM_CONNECTION",
  "controllers": [],
  "executables": {"gennadiy": "/ABSOLUTE/PATH/TO/node_modules/gennadiy-darwin-arm64/bin/gennadiy"},
  "gennadiy_permission_mode": "read-only",
  "models": {"gennadiy": ["gennadiy/EXACT_LOCALLY_ALLOWED_MODEL"]},
  "native_mcp_approved_tools": {"gennadiy": ["describe", "next"]},
  "workspaces": {
    "gui": {"path": "/ABSOLUTE/PATH/TO/gui", "providers": ["gennadiy"]}
  }
}
```

Укажите настоящий Mach-O бинарь из npm-пакета платформы, а не shell-шим
`~/.gennadiy/bin/gennadiy`: shim — скрипт, и worker пинит именно исполняемый
файл. После `gennadiy upgrade` файл меняется, и запуск ждёт `worker consent`.
Вход в Keycloak (`gennadiy login`) и `gennadiy.json` остаются у владельца;
worker их не читает и не меняет, Accord не получает корпоративные токены.
Модель профиля пишется как `provider/model` (например `gennadiy/…`) и должна
быть в локальном `models`. `gennadiy_permission_mode`: `read-only` (по
умолчанию) запрещает правки и shell; `workspace-write` разрешает `edit` и
`bash` обычным shell владельца — у OpenCode нет OS sandbox, это не изоляция.
Headless `gennadiy run` отклоняет любой native «ask», поэтому без
`native_mcp_approved_tools.gennadiy` агент не сможет вызвать `describe`/`next`
и закончит ответом об отказе. Корпоративные MCP (Jira/Confluence/Exchange) в
управляемом запуске выключаются вместе с остальными чужими connectors;
трассировка сессий Langfuse самого gennadiy при этом не отключается.

Некоторые native CLI требуют отдельного согласия для действий Accord даже при
подключённом компьютере. Без него агент может закончить шаг ответом об отказе,
не взяв задачу. Не меняйте общую политику подтверждений ради такого отказа.
Владелец может явно выбрать точные инструменты через локальную опцию
`native_mcp_approved_tools`; по умолчанию она выключена. Границы, пример для
двух тестовых действий и источники —
[Локальные разрешения](native-agent-permissions.md).

## Разрешить управление друг другу

Выполните на каждом ПК своим клиентом, передавая абсолютный путь config:

```text
agent-board worker identity --config PRIVATE_WORKER_JSON
agent-board worker enroll --config PRIVATE_WORKER_JSON
```

На Windows команда начинается с пути к `agent-board.exe`. `identity` показывает
несекретный project-local код управления. Это не token, не registry identity ID
из старой выдачи доступа и не ID профиля. Владелец автоматически может управлять
своим host даже с пустым `controllers` на первом шаге.

Обменяйтесь этими несекретными кодами. На каждом ПК добавьте код второго человека
в локальный `controllers`, затем выполните:

```text
agent-board worker consent --config PRIVATE_WORKER_JSON
agent-board worker run --config PRIVATE_WORKER_JSON
```

`consent` обновляет именно ранее подключённый компьютер через его локальный proof.
Уже работающий worker сначала штатно завершите; второй процесс с тем же state
не запускается. Worker хранит настройки подключения и подтверждения команд в
`state_dir`. Не удаляйте и не копируйте этот каталог ради обхода занятого процесса.

После штатного перезапуска подключение иногда занимает до35 секунд: worker
дожидается окончания прежнего серверного разрешения. Во время ожидания агент
не запускается. Живой или неоднозначно завершившийся исполнитель автоматически
не заменяется.

Оставьте `worker run` работающим. Автозапуск worker при входе в ОС этой командой
не устанавливается. Выход из его терминала останавливает управляемые процессы;
для фоновой службы нужна отдельная настройка от владельца ПК.

## Управление в Accord

Для нового поручения откройте «Управление» → **«Выполнить требование»**,
опишите результат, выберите действующее разрешение команды и нажмите
«Начать выполнение». Дальше выполняется полный цикл: аналитик создаёт задачи,
разработчик реализует их, отдельные ревьюер и тестировщик проверяют результат.
При отсутствии выбранного разрешения форма сохраняет только черновик.
Фактическая поставка этого входа и приёмка — [TASK016](TASK-016-launch-intake.md).

**«Ручной запуск агента»** нужен для отдельного процесса по существующей задаче.
Для изменения файлов укажите задачу; агент сам должен получить её актуальную
аренду. Без задачи можно явно выбрать поручение только на чтение. Это инструкция
агенту, а не дополнительная системная изоляция. В taskless-карточке кнопка
«Выполнить исходное требование» переносит прежний текст в форму полного цикла;
перед отправкой можно его исправить и выбрать разрешение.

Mac enrolled и прошёл WORK195: настоящий Codex прочитал README, получил задачу,
подтвердил остановку, продолжил тот же диалог с новой сессией доски и получил
уточнение. Это приёмка управляемого запуска TASK013; автоматический цикл
TASK014, native Windows и второй физический компьютер проверяются отдельно.
Фактические версии — [TASK013](TASK-013-managed-agents.md).

Для ручной работы уже подключённого Mac в «Давинчи 2.0» выберите «Управление» →
«Ручной запуск агента»: компьютер `mac-main`, папка `gui`, агент Codex, профиль
«Разработчик GUI · Codex». Для изменения кода сначала создайте задачу в проекте
и укажите её номер при запуске. Опишите ожидаемый результат и ограничения.
Агент проверяет право на задачу перед записью; существующие чаты приложения
не превращаются в управляемые процессы автоматически.

На этом Mac настроен user LaunchAgent `com.accord.gui.worker` с запуском при
входе в macOS. Его отдельный private runtime находится в
`~/.config/accord-gui/managed/`; токен и старый GUI bridge сохранены отдельно.
Не запускайте дополнительный `worker run` с тем же state параллельно службе.
Mac должен быть включён и иметь сеть. Пока он выключен или спит, сервер может
сохранить команду в очереди; это ещё не подтверждение выполнения.

Откройте проект GUI → «Управление» → «Ручной запуск агента». Выберите компьютер, разрешённую рабочую
копию и CLI, актуальный профиль агента, напишите задание и нажмите «Запустить».
Один checkout одновременно занят одной работой; для параллельной записи нужен
другой отдельно разрешённый checkout. Версия инструкций профиля закрепляется
при запуске; редактирование профиля не переписывает начатый диалог.

«Остановить» отправляет команду worker. Пока она не подтверждена, панель
показывает ожидание. Принудительное завершение отображается отдельно. Другие
процессы с таким же именем не завершаются.

На Mac/Linux остановка охватывает управляемый CLI и его группу процессов.
Отдельная фоновая служба, которая вышла из этой группы через `setsid`/double-fork,
требует локальной проверки и завершения владельцем. Это не гарантия остановки
всех возможных фоновых писателей в папке. Локальная блокировка checkout
согласует запуски worker; она не является системным запретом записи других
программ. Windows Job Object удерживает созданное им дерево процессов.

«Продолжить» использует тот же сохранённый native диалог и рабочую копию.
Без подтверждённой остановки или сохранённого session ID новый чат не выдаётся
за продолжение. После потери аренды доски агент получает новую сессию и заново
проверяет право на задачу.

Подтверждённое завершение или остановка освобождает рабочую сессию этой попытки
и её занятую задачу. Незавершённая задача возвращается в очередь; отметка «Выполнено» не
появляется автоматически. При продолжении агент получает новое право на работу
и проверяет актуальное назначение задачи. Если завершение не подтверждено,
система сохраняет прежнюю защиту и требует восстановления. После изменения
профиля координатору иногда нужно обновить назначение самой задачи.

«Передать уточнение» сохраняет сообщение в очереди. Для работающего CLI оно
доставляется после текущего шага диалога. Для остановленной работы очередь
доставляется при «Продолжить». Чтобы прервать текущую работу раньше, используйте
отдельную остановку. «Доставлено» означает передачу в native диалог, а не
согласие модели или выполнение требования.

Получение run не заменяет `describe → next` на доске. Код задачи — контекст,
а не аренда. Успешный выход CLI не закрывает задачу и не выдаёт review approve.
Автор, reviewer и tester используют отдельные процессы/серверные сессии.
«Шаг процесса завершён» означает завершение native turn; результат поручения
проверяйте по сообщению агента и состоянию задачи либо полного workflow.

## Первая проверка двух компьютеров

После обновления сервера и подключения обоих worker убедитесь, что оба
участника видят оба компьютера и могут открыть форму запуска на каждом.
Для Mac Codex выберите профиль с provider OpenAI, для Windows Claude — профиль
Anthropic, для Gennadiy — профиль «Gennadiy (OpenCode)»; конкретная модель
должна быть разрешена владельцем локально.

Сначала используйте отдельную тестовую рабочую копию с простым README, без
продуктовых правок. Первый участник запускает чтение README на Windows,
второй — на Mac. Проверьте появление подтверждённого начала работы и ответа.

Затем запустите достаточно длинное тестовое поручение, чтобы проверить
«Остановить». Дождитесь подтверждённой остановки; ожидание команды и offline
не являются её выполнением. Передайте уточнение остановленной работе: оно
должно оставаться в очереди до «Продолжить». После продолжения проверьте ответ
на уточнение и сохранение native conversation ID. Для работы над задачей
продолжение требует нового подтверждения права; при успешном получении аренда
новая, даже когда native диалог остаётся прежним.

Повторите управление с другой учётной записи, поменяв компьютеры местами.
Сохраните только результат, версии клиентов и несекретные коды запусков.
Не пересылайте config/state, токены или полный native transcript.
До этой проверки фактическая работа native Windows и двух физических ПК
остаётся NOT-RUN независимо от сборки `.exe` и локальных тестов на Mac.

## Сбой и восстановление

При пропаже управления worker прекращает свои процессы по локальному watchdog;
offline-интерфейс не обещает мгновенную удалённую остановку. Статус компьютера
отражает последнее наблюдение сервера, а не часы браузера.

После аварии между запуском процесса и записью подтверждения возникает
«Требуется восстановление». Повтор команды, перезапуск с чистым state или новый
host не являются доказательством, что старый процесс остановлен. Worker удерживает
локальную защиту checkout, общую для разных enrollment. Проверьте свои процессы
и локальный журнал с оператором; не убивайте процесс только по старому PID и
не удаляйте защитные файлы вслепую. Автоматический takeover не выполняется.

Такой запуск блокирует только свою рабочую папку: worker один раз сообщает
серверу `delivery_unknown`, пишет в журнал подсказку и продолжает другую работу.
Снять блокировку может только владелец на этом компьютере:

```text
# остановить worker (launchctl/systemd/службу), затем:
agent-board worker recover --config PRIVATE_WORKER_JSON --run RUN_ID
agent-board worker run --config PRIVATE_WORKER_JSON
```

`recover` берёт тот же эксклюзивный lock состояния и отказывается, пока работает
другой процесс worker. Он только читает список процессов (никого не убивает):
если жива любая записанная группа процессов native/проверок этого run — отказ,
ничего не меняется. Иначе run становится `stopped`, защита checkout этого run
снимается, а серверу отправляется `recovered_stopped`; недоставленное
доказательство завершения не переподписывается. Если сеть недоступна, отчёт
остаётся в журнале и уходит при следующем `worker run`. Восстановленный run
остаётся `stopped` после любых перезапусков; `delivery_unknown` для него больше
не отправляется.

Если у run нет записанных групп процессов (его запустил worker старой версии),
проверять нечего, и на macOS/Linux `recover` отказывается. Убедитесь сами, что
ни один агент этого run больше не работает (нет процессов `codex`/`claude`/
`gennadiy` в этой рабочей папке или с этой native-сессией), и повторите с явным флагом:

```text
agent-board worker recover --config PRIVATE_WORKER_JSON --run RUN_ID --unverified
```

С `--unverified` worker печатает предупреждение (вы подтверждаете, что агент
остановлен) и всё равно только читает список процессов своего пользователя:
если найден native-процесс provider, чей рабочий каталог или аргументы
указывают на эту рабочую папку, любой процесс с native session ID этого run или
процесс provider, чей каталог прочитать не удалось, — отказ, ничего не
меняется. Сигналы не отправляются. Причина в отчёте: `owner_recovered_unverified`.

Если сервер больше не знает этот запуск (run архивирован — 404, или запуск уже
продолжен с новой generation/dispatch — 409), отчёт восстановления считается
закрытым: worker пишет об этом в журнал, удаляет отчёт и продолжает работу, а
не завершается при старте. Пока на сервере есть run, требующий восстановления,
и сервер отказывает worker в lease (409), простаивающий worker не завершается:
он пишет подсказку и повторяет опрос с паузой до 30с. Команда остановки для
такого run не подтверждается (доказать остановку нельзя) до `worker recover`.

Штатная остановка worker (SIGTERM) сначала останавливает свои процессы, затем
до10с досылает отчёты и доказательство завершения. Если доставить не успел, но
завершение процесса доказано и записано, после перезапуска шаг закрывается как
`recovered_stopped`, без «Требуется восстановление». Остановка по локальному
сроку шага — тоже обычный `recovered_stopped` (причина `local_deadline`).

Причины, по которым шаг не стартовал, видны в ошибке запуска как короткий код:
`workspace_dirty` (незакоммиченные файлы; указано их число), `target_sha_mismatch`,
`local_budget_exhausted`, `previous_proof_unresolved`, `workspace_busy`,
`registration_rejected`/`registration_unavailable`, `ipc_unavailable`,
`provider_pin_changed`/`workspace_pin_changed` (нужен `worker consent`),
`native_start_failed`, `native_exit_before_session` (CLI вышел до начала
сессии — проверьте вход и версию CLI), `workspace_quarantined`.

Если шаг разработчика прерван (отмена, пауза, срок) с незакоммиченными правками,
worker запоминает отпечаток этих файлов. Когда в ту же папку запускается другой
шаг, а файлы совпадают байт в байт, worker сохраняет их командой
`git stash push --include-untracked -m "accord: interrupted <workflow>/<step>"`
и пишет ссылку stash в отчёт запуска (`git stash apply --index <sha>` вернёт
работу вместе с индексом). Stash выполняется с пустым приватным
`core.hooksPath` и `core.fsmonitor=false`, поэтому hooks репозитория не
запускаются. Если для изменённых файлов в `.gitattributes` (или
`.git/info/attributes`) задан `filter=`, worker фильтры не запускает и ничего не
трогает — ошибка `workspace_dirty`; закоммитьте или уберите файлы в stash сами.
Продолжение того же шага правки не трогает. Изменённые после прерывания файлы,
symlink, submodule или конфликт — ничего не трогается, ошибка `workspace_dirty`.

Если CLI сообщает об отсутствии входа/разрешений, восстановите его обычный
локальный вход и разрешения. Панель не меняет native permissions удалённо.
Полный native transcript остаётся локальным; на сервер отправляются ограниченные
нормализованные сообщения, не raw terminal, environment или reasoning output.

Native интерфейсы сверены по [Codex non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode),
[Claude Code programmatic CLI](https://code.claude.com/docs/en/headless) и
[OpenCode CLI](https://opencode.ai/docs/cli/); форк gennadiy — по локальному
`run --help`/`debug config` версии1.18.10.
Фактические версии и PASS/FAIL/NOT-RUN ищите в TASK013/WORK, а не выводите из
самого наличия этой инструкции.
