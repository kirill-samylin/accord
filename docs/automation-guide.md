# Как поручить требование команде Accord

Инструкция для интерфейса TASK014. Фактически установленную версию и результаты
проверок смотрите в [checkpoint](TASK-014-automation.md): наличие этого файла
в репозитории само по себе не означает обновления сервера.

## Настроить один раз

1. Откройте общий проект Accord под своим токеном. У участников должны быть
   отдельные учётные данные и доступ к этому же проекту.
2. На компьютере, который будет выполнять работу, нужны локальная копия Git,
   установленный Codex/Claude с собственным входом и работающий Accord worker.
   [Подключение компьютера](managed-worker-guide.md). Владелец локально выбирает
   рабочую папку, разрешённых управляющих и проверки проекта. Это отдельное
   согласие: вход на сайт и роль редактора компьютер не подключают.
   [Локальная настройка автоматического цикла](automation-worker-setup.md)
   описывает проверку config и получение consent digests установленным клиентом.
3. Откройте **«Выполнить требование» → «Подготовить команду»**. Создайте четыре
   профиля: аналитик, разработчик, ревьюер и тестировщик. Их инструкции можно
   редактировать. Профиль описывает роль; реальный процесс запустит worker.
4. Нажмите **«Настроить запуск»**. Выберите подключённый компьютер и папку,
   примите её актуальное локальное согласие, назначьте четыре профиля и Codex
   либо Claude для каждой роли. Укажите участников, обязательные реальные
   проверки, пределы времени, числа задач и исправлений, срок разрешения.
   Компьютер должен объявлять поддержку автоматизации.
5. Чтобы подавать требования из Codex/Claude, явно включите в этом разрешении
   **задания из клиента** для нужных участников. Без этого браузер и клиент
   не получают одинаковых прав на запуск автоматически.

Проверки привязаны к конкретному проекту: фиксированный локальный запуск,
настоящие тесты и проверяемый отчёт. Если у нового пустого репозитория ещё нет
требования и способа проверки, их нужно определить при подготовке проекта.
Пустой отчёт или выход программы с кодом0 не засчитываются как выполненные тесты.

## Каждый рабочий запуск

1. В **«Выполнить требование»** опишите желаемый результат, ограничения и
   критерии готовности. Приложите существенный контекст проекта.
2. В поле **«Команда и разрешение»** выберите действующее разрешение и нажмите
   **«Начать выполнение»**. Пункт **«Сохранить черновик без запуска»** только
   сохраняет текст и не запускает агентов.
3. Откройте карточку требования. Аналитик составит план, разработчик выполнит
   задачи, отдельные ревьюер и тестировщик проверят точный результат. Замечания
   запускают ограниченный цикл исправлений с новым review и QA.
4. Отвечайте на вопросы в карточке. При ожидании видно причину: например,
   компьютер недоступен, разрешение истекло, рабочая папка занята или необходим
   ответ человека. Итог содержит задачи, локальный Git SHA и результаты проверок.

Компьютер исполнителя должен оставаться включённым, worker — подключённым.
Браузер можно закрыть: сервер и worker продолжают работу в пределах разрешения.
Один цикл выполняется последовательно в одной выбранной рабочей копии. Другая
копия репозитория не получает новые коммиты автоматически; push/merge/deploy
требуют отдельного поручения.

## Управлять ходом работы

| Действие | Результат |
| --- | --- |
| Пауза | Останавливает дальнейшее выполнение и запрашивает остановку текущих процессов. Ждите подтверждённого состояния. |
| Продолжить | Продолжает разрешённый незавершённый этап с сохранённым точным диалогом; новая аренда защищает задачу от прежней попытки. |
| Передать уточнение | Сохраняет сообщение для следующего хода агента. Уже выполняющаяся команда не переписывается задним числом. |
| Пересмотреть план | После паузы явно меняет план с учётом уже полученных результатов. |
| Отменить | Запрашивает остановку и завершает цикл после подтверждения выхода процессов. |

«В очереди», «отправлено» и «компьютер недоступен» не означают, что процесс уже
остановлен. Если владение процессом неизвестно, требуется локальное восстановление;
не запускайте второго писателя в той же папке.

## Написать из Codex или Claude

Подключите обычный stdio MCP bridge с явным ID нужного проекта и своим приватным
token file. Выбор проекта в браузере не меняет проект MCP-клиента. Настройка
клиента приведена в [client setup](client-setup.md).

Можно дать клиенту такое поручение, подставив ID и версию разрешения из Accord:

> Через MCP Accord открой сессию и передай это требование в workflow_submit
> с разрешением POLICY_ID версии VERSION. Требование: … Сохрани ID workflow,
> следи за его состоянием и сообщай вопросы. Для изменения задания используй
> workflow_command. Выполнение поручено команде Accord.

Повтор одной отправки с тем же request_id возвращает прежний результат;
новый request_id создаёт новое требование. Сам код разрешения не является токеном
доступа. Клиент агента внутри этапа не получает право запускать другие циклы.

## Второму участнику

Для работы в браузере достаточно собственной учётной записи и доступа к общему
проекту. Управлять уже подключённым компьютером можно после добавления владельцем
в его локальный и серверный списки управляющих и разрешение команды.

Чтобы выполнять работу на своём компьютере, участник отдельно устанавливает
подходящий worker и native CLI, входит в свой Codex/Claude, клонирует репозиторий,
подключает свою рабочую папку и подтверждает локальное согласие. Токен первого
человека, host proof и вход провайдера ему не передают. Для Windows нужен native
исполняемый файл CLI; сборка Windows не заменяет проверку на самом компьютере.
