## 1. Цель и границы

REQ-01. Один экземпляр координирует один проект: эпики, задачи с ролевой
меткой, зависимости, аренды и общий журнал. Два человека на разных машинах
могут независимо запускать агентов и видеть общее состояние работы.
Сервис не исполняет код, не запускает/останавливает агентов, не хранит код,
диффы, скриншоты или полный контекст модели; хранит краткий текст и ссылки.
Он не изменяет GitHub и не принимает решения о маршрутизации вместо агентов.

REQ-02. Пилот TASK-001 включает локальные токены, сессии, Go/SQLite,
эпики/задачи, очередь, зависимости, попытки, доказательства, аренды с fencing,
идемпотентные мутации, события, REST, MCP и CLI. Обязательны `create`, `get`
и `link`: без них сценарий запроса архитектору нельзя воспроизвести.
Пилот не является завершённой V1 и не обещает совместимость с любым MCP-клиентом.

REQ-03. Полная V1 дополнительно включает конфигурацию процесса со схемой и
историей, GitHub/OAuth авторизацию, заметки, все роли и правила исходного ТЗ,
GitHub webhooks, уведомления, импорт/экспорт, статистику, две страницы веба,
шаблон Давинчи и пакеты выпуска. Эти требования сохранены в §9 и roadmap;
они не превращаются в неявный объём текущего пилота.

## 2. Идентификация и доступ

REQ-04. Участник — владелец локального токена; токен имеет имя машины и срок.
Пилотный локальный токен допускает перечисленные роли; ограничение scopes — V1.
В БД хранится только проверочный хеш случайного
высокоэнтропийного токена, исходное значение показывается один раз.
CLI читает токен из переменной окружения; журнал и ошибки его не содержат.
Локальная CLI позволяет отозвать токен по ID. Отозванный/истёкший токен
не даёт выполнять новые операции, включая replay.

REQ-05. `describe` открывает серверную board-сессию с фиксированными ролью,
участником, машиной и клиентским `run_id`. `session_id` генерирует сервер;
клиентский `run_id` — метка, не доказательство независимости. Повтор открытия
с тем же request_id возвращает прежнюю сессию. Операции сессии требуют
тот же токен; чужой session_id недостаточен для доступа.

REQ-06. Пилотные роли: `coordinator`, `analyst`, `architect`, `developer`,
`reviewer`, `tester`, `human`. `architect` — singleton; остальные нет.
Одна сессия держит не более одной задачи. Координатор создаёт и связывает
работу и запускает исполнителя у себя; исполнитель открывает свою сессию и
сам вызывает `next`. Передачи координаторской аренды исполнителю нет.

REQ-07. Независимая проверка выполняется другой server-generated сессией,
чем авторские попытки проверяемого результата. Один человек вправе запустить
разработчика и отдельного ревьюера. Сервер не доказывает различие людей,
моделей или процессов по произвольным строкам клиента; это организационное
ограничение, а не обещание криптографически доказать независимое мышление.

## 3. Данные, очередь, переходы

REQ-08. Эпик: ключ `E-N`, заголовок ≤200 символов, описание ≤16 КиБ,
владелец/приоритет/области, состояние `open|done|cancelled`.
Задача: ключ `T-N`, обязательные эпик, роль, заголовок и описание;
приоритет (1 — высший), области, requester, состояние, попытки, evidence,
опциональные target_task/target_commit для проверки. Ключи уникальны и
генерируются сервером. Категория, сложность и external_id относятся к V1.

REQ-09. Состояния задачи: `created`, `ready`, `in_progress`, `done`,
`cancelled`. Блокировка — вычисляемый признак, не состояние.
Только `next`/точечный захват внутри `next` переводит ready → in_progress.
Очередь учитывает роль, отсутствие действующей аренды и блокирующих связей;
сортировка: priority, ready_at, ключ. Выдача требует open-эпик; отмена эпика
останавливает новые захваты, не удаляя историю дочерних задач. Его возврат
в open возобновляет очередь. Выполненные задачи не выдаются в next.
Чтение get доступно явно, включая доказательства и историю попыток.

REQ-10. В пилоте create сразу даёт ready; стадия created и перевод
заказчиком/координатором created → ready сохраняются для полной V1.
Заказчик/координатор отменяет с причиной
и восстанавливает cancelled → ready с причиной. Держатель действующей аренды
завершает in_progress → done либо освобождает → ready через release.
Обычное изменение метаданных не подменяет переход состояния.
Роль reviewer/tester вправе переоткрыть developer; developer — analyst/
architect; coordinator/human — любую задачу. Переоткрытие done → ready
требует причину и evidence_ref на существующую задачу с доказательством дефекта.
Чужую живую аренду нельзя снять отменой, изменением или переоткрытием.

REQ-11. Попытка хранит server session_id, участника, run_id, machine,
generation, начало/конец, причину, ветку и evidence. История не стирается
при истечении, release или повторном выполнении. Ветка — ссылка для
следующего исполнителя, не разрешение автоматически продолжить чужой код.
В пилоте области — метки, не гарантия блокировки файлов/путей на машине.

REQ-12. Связи пилота: `blocks`, `contract_of`, `spawned_by`, `related`.
A blocks B: B допускается к захвату после успешного результата A.
`contract_of` в пилоте имеет ту же проверку готовности; в V1 настраивается
момент поставки контракта. `spawned_by` и `related` не блокируют.
Ссылка хранит condition (`completed|approved|passed`); отсутствие condition
означает успешный результат роли, а не любой done. Для reviewer это approve,
для tester passed. Циклы blocks/contract_of и ссылки на отсутствующее запрещены.
Связь живого потребителя меняет только держатель с его текущим generation;
для незахваченного потребителя — координатор либо его заказчик. Unlink
подчиняется тем же правам и аудиту; он не стирает обязательность ранее
назначенного review/test для закрытия эпика.
`duplicate_of` и связи эпиков входят в расширение V1.

## 4. Доказательства и приёмка

REQ-13. Сервер валидирует форму evidence и актуальность внутренних ссылок;
он не проверяет содержание артефактов или выполнение команд без интеграции.
В пилоте developer: `commit` (40/64 hex), непустой `run_summary` ≤1 КиБ;
analyst/architect: непустые `artifact` (массив ссылок) и `summary`;
human: непустой `answer`. Coordinator: непустой `summary`.
PR в пилоте опционален; обязательность реального PR вводится вместе с
интеграцией и конфигурацией. Локальный путь/ссылка не доказывает существование.

REQ-14. Reviewer: `verdict=approve|changes_requested|blocked`,
`verified_commit`, `findings`. Tester: `result=passed|failed|not_run|not_applicable`,
`verified_commit`, `run_summary`. Задача проверки обязательно ссылается на
target_task developer и target_commit; target_generation фиксируется сервером.
Для ещё не завершённого target binding generation откладывается до первого
claim проверки; до done target и совпадения SHA проверка не готова к claim.
verified_commit совпадает с target_commit и актуальным commit target, а
generation target совпадает с зафиксированным поколением проверки.
Сессия проверяющего не совпадает
с авторскими сессиями результата/попыток, указанными в provenance.

REQ-15. «Проверка завершена» не означает «проверка пройдена». Отрицательный
вердикт сохраняется в done, но не удовлетворяет положительному gate.
`not_applicable` требует отдельного явного принятия применимости в полной V1;
в пилоте не удовлетворяет passed. Отмена обязательной проверки не подменяет
положительное доказательство и не разрешает закрытие эпика.

REQ-16. Approve/passed относится к конкретным target_generation и target_commit.
Переоткрытие target (в том числе с тем же SHA) или изменение commit делает
прежнее подтверждение устаревшим; ready target не считается актуальным.
Историческая проверка не удаляется, но её gate закрывается. Незавершённый
потребитель не получает новый захват/право завершения, пока gate не восстановлен.
Изменение источника уже завершённого эпика переоткрывает эпик; завершённые
результаты сохраняются для аудита, а новый цикл проверки оформляется явно.

REQ-17. Эпик закрывается coordinator/human только когда все задачи terminal,
нет действующих аренд и все обязательные gates удовлетворены актуальными
положительными доказательствами. Отрицательные review/tester не засчитываются.
Добавление новой задачи или переоткрытие задачи открывает эпик снова.
Историческая stale/отрицательная проверка заменяется новым положительным
циклом, не блокирует эпик навсегда: для каждого target сохраняется обязанность
иметь актуальную положительную проверку каждой ранее назначенной роли
reviewer/tester (target key+generation+SHA), даже после unlink старой зависимости.
Обязательства target учитываются во всём экземпляре, даже если проверяющий
находится в другом эпике. Для target+роли+актуальных SHA/generation действует
последняя назначенная проверка по серверному порядку создания: новый
pending/negative не обходится старым approve, новый positive заменяет negative.
Новая проверка и инвалидация зависимостей атомарно переоткрывают затронутые
завершённые эпики, сохраняя историю задач.

## 5. Аренды и отказоустойчивость

REQ-18. Аренда задачи и singleton-роли содержит owner session_id,
монотонное generation и expires_at по серверному времени. При каждом новом
захвате generation увеличивается и не сбрасывается после restart/release.
Мутация задачи проверяет owner, generation, now < expires_at, роль и состояние
в той же транзакции, где меняет данные. Равенство now=expires_at уже просрочено.
Переданное ненулевое generation означает запрос к конкретной аренде:
после expiry/release он не переключается на административные права requester/
coordinator. Для незахваченной работы административные update/link используют
generation=0 (поле можно опустить), сохраняя обычную проверку прав.

REQ-19. Истечение действует немедленно по времени, даже если sweep не был
запущен. Любая конкурирующая операция и очередь видят аренду истёкшей;
сервер материализует закрытие попытки и lease_expired ровно один раз.
Просроченный heartbeat не восстанавливает ни задачу, ни singleton-роль.
Старый владелец обязан открыть новую сессию после утраты singleton-роли и
заново получить задачу; новое поколение не возвращается как «продление».

REQ-20. Новая успешная разрешённая мутация продлевает сессию/singleton.
Аренду задачи продлевает только мутация этой живой аренды с проверенным
generation (update/comment/link) либо явный heartbeat. Создание другой задачи
не продлевает удерживаемую задачу. Ошибка, GET, events, tools/list,
describe/replay старого ответа не продлевают. Heartbeat продлевает только
неистёкшие аренды; stale token/generation отвергает весь heartbeat атомарно.
TTL пилота: задача и роль 15 минут; клиентский heartbeat не реже 5 минут.
Ограниченная конфигурация TTL валидируется при запуске, не меняется на лету.

REQ-21. Клиентский heartbeat — отдельная обязанность интеграции клиента:
наличие MCP-инструмента не создаёт фонового таймера в Claude Code/Codex.
При потере связи, неоднозначном ответе или LEASE_LOST клиент прекращает
локальные изменения, восстанавливает связь и сверяет серверное владение.
Сервис не способен остановить файлы/процесс на отключённой машине.
Fencing защищает серверные операции, но не является файловым distributed lock.

## 6. Повторы и события

REQ-22. Каждая мутация содержит непустой request_id (≤128 символов).
Ключ уникален в пределах токена+board-сессии; открытие сессии — токена.
Операция, канонический payload, изменения, события и сохранённый ответ
фиксируются одной транзакцией. Повтор идентичного запроса возвращает сохранённый
ответ без повторного изменения/продления. Другой payload/операция с тем же
ключом → IDEMPOTENCY_CONFLICT. В пилоте результаты не удаляются автоматически.
Новая мутация после ошибки использует новый request_id; транспортный JSON-RPC
id не заменяет бизнес request_id. Токен проверяется и при replay.

REQ-23. Журнал только на добавление, id — монотонный курсор; время серверное.
Секретов/токенов в payload нет. Изменение состояния и его событие атомарны.
`high_water` — последний id на сервере, не отметка прочтения.
Events возвращает `next_cursor` последней просмотренной записи страницы,
`high_water`, `has_more`. Фильтры фиксируются клиентом на весь проход.
Limit 1..200, по умолчанию 100; пропущенные фильтром записи можно пройти,
но непоказанные подходящие записи нельзя перескочить. В пилоте high_water
есть только в EventsPage; другие business DTO не получают меняющиеся метаданные.
Нет since_cursor — начальный курсор 0; исторический поток читается явно.

REQ-24. Курсор и my_tasks не заменяют checkpoint координатора. В репозитории
клиента остаётся краткое состояние: принятое решение, незавершённые проверки,
следующий шаг, последний обработанный cursor. Контекст модели сервис не хранит.

## 7. Транспорты и эксплуатация пилота

REQ-25. REST и MCP используют один сервис правил, одинаковые DTO и коды
ошибок. MCP имеет ≤12 инструментов; фиксированный список не меняется после
describe. Роль проверяется сервером при вызове. Инструменты могут фильтроваться
только по авторизации запроса, не по побочному эффекту выбора роли в соединении.
Поддерживаемые protocol/SDK фиксируются в architecture/go.mod и проверяются
SDK-клиентом; реальные Claude Code/Codex проверяются отдельно.

REQ-26. Локальный HTTP слушает loopback; удалённый запуск требует TLS перед
сервером и отдельной эксплуатационной проверки. База SQLite WAL, миграции
при старте, все мутации транзакционны. Один процесс/одна база на проект.
Пилот не обещает HA, автоматический failover, zero-downtime migrations.
Путь к данным и секретам — игнорируемый .local/, не Git.
Новый DB создаётся с 0600 до SQLite IO; существующие DB/WAL/SHM/journal
должны быть regular 0600 без symlink. Каталог не может быть group/other-writable.
Небезопасные существующие файлы вызывают отказ без chmod/перезаписи.

## 8. Приёмка пилота

| AC | Проверяемый результат |
| --- | --- |
| 01 | Два конкурентных next на двух DB-подключениях дают одного владельца |
| 02 | Граница TTL, выключенный sweep, restart и старое generation не обходят аренду |
| 03 | Пустая очередь, singleton занят, задача уже взята дают понятные ответы |
| 04 | Повтор create/next/transition/link/heartbeat не дублирует результат и события |
| 05 | Payload conflict, чужая session, отозванный токен отклоняются |
| 06 | Пагинация с limit=1 и фильтром не теряет события при новых записях |
| 07 | changes_requested/failed/not_run/stale SHA/саморевью не открывают gate |
| 08 | Цикл зависимостей отвергается; положительный актуальный результат открывает gate |
| 09 | Developer создаёт architect-запрос, release, architect done, новый developer next |
| 10 | REST, MCP SDK и CLI проходят create/get/link/next/done; данные переживают restart |
| 11 | Ошибочные и читающие запросы не продлевают аренды, heartbeat не оживляет expired |
| 12 | Независимый reviewer проверяет конкретную версию; после approve отдельный tester |

Сквозной пилот на двух физических машинах с Claude Code и Codex остаётся
обязательным внешним этапом: два процесса на одном ПК не являются его PASS.
Нагрузка, все целевые ОС, production security и OAuth проверяются отдельно.

## 9. Полная V1: сохранённые требования

V1-01. GitHub OAuth allowlist/org/team, браузерный вход, token create/list/revoke,
OAuth MCP по discovery/resource metadata/PKCE и проверке audience; не «просто
тот же bearer». Совместимость заявляется по проверенной матрице клиентов.
V1-02. Версионируемая YAML-конфигурация, JSON Schema, config validate/apply,
роли/матрицы прав/условия доказательств/TTL/areas/правила block|warn|off.
Единая терминология: `strict` исходника нормализуется в `block`.
V1-03. Epic-owner off|warn|block, shared_roles, explicit handoff; human eligibility
по category/complexity; singleton planner включается только после отдельного
решения, пилот использует coordinator без singleton. Detect duplicates и
area overlap с аудитом; alias области разрешается в один канонический root,
подпуть не обходит проверку пересечения. Сервис не читает файловую систему клиента.
V1-04. Notes role/epic с источником, правом удаления и лимитами; комментарии,
tokens_spent по попыткам, correction events, полная статистика без рейтинга.
V1-05. Webhooks PR/CI/review: проверка подписи, dedup delivery id, target SHA,
unmatched журнал. Пропущенная доставка означает completeness=unknown;
без GitHub API восстановление через ручную redelivery. Сервис не выдумывает
актуальность PR/CI по отсутствию события. Исходящие подписанные уведомления
с retries и журналом; эскалация вопросов 48ч по умолчанию.
V1-06. JSONL import по external_id, конфликтная политика без переписывания
живых аренд, export и согласованный SQLite backup; мигратор Давинчи отдельный.
V1-07. Веб «Моя очередь» и «Состояние», human claim/answer/reopen, токены,
read-only config/history, аудит и статистика. Визуальная реализация после макетов.
V1-08. Linux/macOS amd64/arm64, Windows amd64, бинарники/контейнер/systemd,
TLS reverse proxy либо обоснованная встроенная реализация; JSON logs, metrics,
rate limits, secret scan. Полная документация EN + ключевые разделы RU,
шаблон Давинчи, handoff checkpoint, backup/restore и процедура обновления.
V1-09. Нагрузочные цели исходника (20 сессий, 2 000 задач, 200 000 событий/год,
p95≤50мс, RSS≤128МиБ на 1vCPU/512МиБ, старт≤1с) — проверяемые цели V1,
не измеренные характеристики пилота; benchmark фиксирует метод и стенд.
